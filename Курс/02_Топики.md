## M0. Мир IT с нуля (неделя 1) — *Ch.01*

**Цель:** понять, из чего состоит программный продукт и кто его делает.

Топики:
- 0.1 Что такое программа, приложение, система, сервис. Зачем бизнесу ПО.
- 0.2 Клиент и сервер: что происходит, когда вы нажимаете «Заказать» (браузер → интернет → сервер → база → ответ).
- 0.3 Frontend, Backend, База данных, API — четыре кирпича.
- 0.4 Окружения: dev / test / stage / prod. Релиз, баг, хотфикс.
- 0.5 Команда: заказчик, PO, PM, аналитик, архитектор, разработчик, тестировщик, DevOps, дизайнер.
- 0.6 Жизненный цикл ПО (SDLC): идея → требования → дизайн → разработка → тест → внедрение → поддержка.
- 0.7 Базовые термины (глоссарий 50 слов): сервер, протокол, IP, DNS, HTTP, JSON, репозиторий, ветка, деплой.

Аналогия: ресторан. Зал = frontend, кухня = backend, склад = БД, официант = API.
Ошибки: путать «сайт» и «систему»; думать, что аналитик пишет код.
Практика: нарисовать путь заказа пиццы через IT-компоненты.
Тест: 10 вопросов на терминологию.

## M2. Системное мышление (неделя 3) — *Klimenko 2021, гл. 1–2, 4, 5, 9; конспект: [03_Конспект_Клименко.md](03_Конспект_Клименко.md)*

Топики:
- 2.1 Что такое система: элементы, связи, структура, цель, границы, среда (гл. 1.1–1.3).
- 2.2 Классификация систем: простые/сложные, открытые/закрытые, социотехнические.
- 2.3 Эмерджентность: целое больше суммы частей — на примере «Библиотеки» и «Службы доставки».
- 2.4 Обратная связь и упреждающая обратная связь (гл. 1.5–1.6): как метрики управляют системой.
- 2.5 Модель «чёрного ящика»: вход → преобразование → выход; связь с контрактом API.
- 2.6 Модели и моделирование (гл. 2): ментальные, семантические, статические и динамические; зачем аналитику модели.
- 2.7 Система управления: управляемость, наблюдаемость, функции управления (гл. 4).
- 2.8 Базовая методика системного анализа (гл. 9): формулировка проблемы → структурирование проблематики → конфигурирование (заказчик, ЛПР, активные и пассивные участники) → постановка задачи и цели → критерии → альтернативы → ограничения → моделирование → решение → реализация.
- 2.9 Главный вывод: определить истинную цель важнее, чем найти лучшую альтернативу; опасность подмены цели средством.
- 2.10 Вспомогательные методы анализа причин: 5 «почему», диаграмма Исикавы.

Ошибки: сразу решать «как», не уточнив проблему; принимать формулировку заказчика за истину.
Практика: разобрать «Библиотеку» как систему (границы, акторы, потоки, обратные связи), пройти шаги 1–5 методики на реальной «боли» и записать цель и 3 критерия успеха.

## M3. Сбор и управление требованиями (неделя 4) — *Ch.02*

Топики:
- 3.1 Что такое требование. Потребность → бизнес-цель → требования → решение.
- 3.2 Уровни: бизнес-, стейкхолдеров, решения (функциональные FR, нефункциональные nFR), переходные.
- 3.3 Стейкхолдеры: карта влияния/интереса, SME.
- 3.4 Выявление: интервью, воркшопы, наблюдение, анкетирование, анализ документов, прототипирование, мозговой штурм.
- 3.5 Хорошее требование: атомарное, проверяемое, однозначное, трассируемое. «Плохие слова» (быстро, удобно, и т. д.).
- 3.6 Форматы: свободный текст, «Система должна…», User Story + Acceptance Criteria (Given/When/Then), Use Case.
- 3.7 Ограничения, допущения, риски (R., AS.).
- 3.8 Приоритизация: MoSCoW, Kano, WSJF, голосование.
- 3.9 Согласование и управление изменениями (Change Request), версии.
- 3.10 Матрица трассировки: цель → потребность → BR → FR → тест-кейс.
- 3.11 Документы: BRD, GAP-анализ, Solution Overview.

Ошибки: смешивание «что» и «как»; требование без критерия приёмки.
Практика: интервью-гайд (15 вопросов), 15 требований FR/nFR, матрица трассировки.

## M4. Бизнес-процессы (неделя 5) — *Ch.02, Ch.04*

Топики:
- 4.1 Что такое процесс. AS-IS, TO-BE, SHOULD-BE.
- 4.2 Нотации: VAD (цепочка добавленной стоимости), eEPC (ARIS), Cross-functional flowchart, BPMN, UML.
- 4.3 BPMN 2.0 — рабочее ядро: пулы и дорожки, задачи (user/service/manual/script), события (start/intermediate/end; throwing/catching; boundary: interrupting / non-interrupting), шлюзы (XOR, AND, OR), потоки (sequence / message), подпроцессы, артефакты.
- 4.4 Типичные паттерны: согласование, эскалация по таймеру, повтор, параллельная обработка.
- 4.5 Инструменты: Bizagi, Camunda Modeler, draw.io, Visual Paradigm, Miro, ARIS.
- 4.6 Метрики процесса: время цикла, стоимость, SLA, KPI.

Ошибки: «спагетти»-диаграммы; нет конечного события; смешение потоков сообщений и последовательности.
Практика: BPMN «Оформление заказа» (AS-IS + TO-BE) + 3 KPI.

## M5. Архитектура ПО (неделя 6) — *Ch.03*

Топики:
- 5.1 Зачем аналитику архитектура: для интеграций, nFR, оценок.
- 5.2 Контекстная диаграмма (система и окружение), актёры, внешние системы.
- 5.3 Архитектурные виды: логический, физический, интеграционный, развёртывание.
- 5.4 Клиент-серверные паттерны: Desktop, толстый/тонкий клиент, 2-tier, 3-tier / N-tier (Presentation, Business Logic, Data).
- 5.5 Монолит vs SOA vs микросервисы (MSA): плюсы, минусы, когда что.
- 5.6 Интеграция между компонентами (БД-линк, web-сервисы, очереди).
- 5.7 Масштабирование: вертикальное/горизонтальное, кластеры, балансировка, шардирование.
- 5.8 Кэширование: Key-Value, Redis, IMDG, политики вытеснения (FIFO, LRU), инвалидация.
- 5.9 Нефункциональные характеристики: производительность, доступность (99.9%), отказоустойчивость, безопасность (VPN, SSO, шифрование), логирование, мониторинг.
- 5.10 Сетевой и инфраструктурный уровень: DNS, порты, NAT, балансировщик, контейнеры (Docker/Kubernetes — обзор).
- 5.11 Нотация C4 (Context → Container → Component → Code) — современный способ рисовать архитектуру.
- 5.12 ADR (Architecture Decision Record): фиксация решений.

Практика: схема архитектуры «Заказ еды» (монолит → микросервисы) + ADR.

## M6. Поведение системы и UX (недели 7–8) — *Ch.04*

Топики:
- 6.1 Актёры (люди, системы, время) и их цели.
- 6.2 Use Case: основной поток, альтернативные, исключения, предусловия, постусловия, гарантии (по Cockburn).
- 6.3 UML Use Case Diagram: include / extend.
- 6.4 UML Activity Diagram: действия, ветвления, fork/join, swimlanes, поток объектов.
- 6.5 UML Sequence Diagram: линии жизни, синхронные/асинхронные сообщения, возвраты, фрагменты alt / opt / loop.
- 6.6 Выбор нотации: что для какой задачи.
- 6.7 UX для аналитика: пользовательские пути (CJM), макеты, wireframes, прототипы (Figma), валидации полей, тексты ошибок, состояния экрана (пусто/загрузка/ошибка).
- 6.8 Описание экрана: поля, типы, обязательность, маски, действия, права.
- 6.9 UML Class Diagram: классы, атрибуты, связи (ассоциация, агрегация, композиция, наследование), кратности, enum.

Практика: Use Case + Activity + Sequence + wireframes + Class Diagram для «Оформления заказа».

## M7. Данные (неделя 9) — *Ch.05*

Топики:
- 7.1 Зачем моделировать данные. Сущность, атрибут, связь.
- 7.2 Концептуальная → логическая → физическая модель.
- 7.3 Типы связей 1:1, 1:n, m:n (+ ассоциативная таблица), идентифицирующие/неидентифицирующие.
- 7.4 Ключи: первичный, внешний, суррогатный vs естественный; ON DELETE (RESTRICT/CASCADE/SET NULL).
- 7.5 Нормализация (1НФ–3НФ) и разумная денормализация.
- 7.6 Индексы: B-Tree, уникальные, когда помогают/мешают.
- 7.7 Типы данных, соглашения об именовании, справочники.
- 7.8 Объекты БД: таблицы, представления, последовательности, триггеры, процедуры.
- 7.9 SQL: SELECT / WHERE / ORDER BY / DISTINCT, JOIN (inner/left), агрегаты (COUNT, SUM, MIN, MAX, AVG), GROUP BY / HAVING, подзапросы, EXISTS / NOT EXISTS, INSERT / UPDATE / DELETE.
- 7.10 Транзакции: COMMIT / ROLLBACK / SAVEPOINT, ACID, блокировки.
- 7.11 Диаграмма состояний (State Machine): жизненный цикл заказа/документа, переходы, события, условия.
- 7.12 SQL vs NoSQL, хранилища и аналитика (DWH, ETL/ELT) — обзор.
- 7.13 Качество данных, персональные данные, маскирование (актуально для 2027).

Практика: ER + DDL + 15 SQL-запросов (SQL-тренажёры), State Machine заказа.

## M9. Брокеры сообщений (неделя 12) — *Ch.06 (MQ), 06.1 Kafka, 06.3 RabbitMQ*

Топики:
- 9.1 Очередь сообщений: producer, consumer, queue, брокер; push vs pull; персистентность, порядок (FIFO), подтверждения.
- 9.2 RabbitMQ: exchange (direct / fanout / topic / headers), binding, routing key; типы очередей (classic, quorum, stream); durable / autoDelete.
- 9.3 Apache Kafka: topic, partition, offset, consumer group, ключ сообщения, порядок внутри партиции, репликация (leader / follower), retention.
- 9.4 Сравнение MQ и Kafka (кто хранит, кто удаляет; одна очередь vs лог).
- 9.5 Надёжность: retry, fallback, reject, DLQ (dead letter), at-least-once / exactly-once, идемпотентность потребителя.
- 9.6 Шаблоны: Outbox, Saga, Event Sourcing, CQRS (обзор).
- 9.7 Описание в спецификации: топик, ключ, схема (Avro / JSON Schema), версия, ретеншн, партиции.
- 9.8 AsyncAPI 3.x: каналы и операции.

Практика: событийная интеграция «OrderCreated» (топик + ключ + схема + сценарии ошибок).

## M13. Капстоун-проект (недели 15–16)

Сквозной проект «Сервис заказа еды» или «Электронная библиотека». Требуется:
1. Описание системы и бизнес-целей.
2. BPMN AS-IS / TO-BE.
3. Требования (≥ 30), приоритизация, трассировка.
4. Use Case ×3, Activity, Sequence.
5. ER-модель, DDL, State Machine.
6. Схема архитектуры (C4), ADR.
7. OpenAPI (≥ 8 методов) и описание события (Kafka/RabbitMQ).
8. (Бонус) AI-фича.

Критерии: полнота, согласованность артефактов, ясность, проверяемость.
